% Abstract

\begin{abstract}
    A fast-paced action game might appear straightforward on the surface. Characters move, attack and react to incoming threats. But behind a truly engaging action game lies a complex web of interconnected systems. Movement, combat, enemy behavior, physics and even sound and animation must all work together. How does such a huge amount of interaction remain architecturally clean? Project Polearm is a demo for a hack-and-slash video game, developed for the Maturitätsarbeit 2026 by Rodin Arslan and Zhile Zhu of the department G23g at the Kantonsschule Baden. This \emph{Technical Documentation} describes the technical structure and organization as well as the core architectural decisions and systems of the game, alongside some insights into the development process.

    The project, created using the Godot engine, encompasses roughly 11,800 lines of GDScript and C\# code, the majority of it handwritten, with documented AI assistance. We sought to learn how to implement features found in hack-and-slash games by doing, but it did not stop there. We also aimed to do so cleanly and with thought. Not only did we ask ourselves, \enquote{What does an action game do and how is it designed?}, but we also asked: \enquote{How can developers build a complex game from many interlocking systems without losing control of the codebase?}

    Project Polearm demonstrates the core features expected of the genre, but it also showcases the intersection of data-driven and object-oriented programming, combined with design patterns and practices from the game development industry. We utilized our modular architecture and components to create a mobile and dynamic player character, as well as five different enemy variants working together to stop the player, all placed in a series of combat encounters within a hand-crafted level.

    The project was the result of our exploration of philosophies and paradigms, modular systems programming, finite state machines, complex entity management and the abstraction of physics for player enjoyment. We reasoned about program architecture and structure, and how they might be cleanly implemented to create engaging gameplay systems. Not only should the gameplay be intuitive, but so should the development experience, which is why we made many efforts to streamline development and to develop, test and iterate efficiently.

    As this document aims to highlight the technical development of Project Polearm, please consult the main accompanying report for information about the game design and research of this project.

    This document starts with \textbf{Chapter~\ref{sec:organization}: Organization}, which documents the file structure of the project, how directories are organized and how to navigate the project. \textbf{Chapter~\ref{sec:design-decisions-and-goals}: Design Decisions and Goals} then explains our philosophies for the development process. These led us to use certain patterns and paradigms across the entire project, each with its own consequences for the project.

    The next two chapters, \textbf{Chapter~\ref{sec:architecture-and-systems}: Architecture and Systems} and \textbf{Chapter~\ref{sec:procedures-and-algorithms}: Procedures and Algorithms}, dive into the code of Project Polearm. The former does this on a macro level, explaining the structure of the most far-reaching systems of the game and how they interconnect to form its architecture. The latter does this on a much smaller but more detailed level. Algorithms which drive player and enemy behavior are showcased in pseudocode diagrams alongside explanations of the design choices which led to their final form.

    \textbf{Chapter~\ref{sec:tooling-and-developer-experience}: Tooling and Developer Experience} walks through how we sought to make our lives easier during development, with tools, scripts and clever usage of the aforementioned design patterns. It is followed by a retrospective in \textbf{Chapter~\ref{sec:post-mortem}: Post-Mortem}, where we ask what went well, what went less well, and how we dealt with issues that came up. Finally, \textbf{Chapter~\ref{sec:appendix}: Appendix} provides additional information about the project, and a glossary of terms used in this document.
