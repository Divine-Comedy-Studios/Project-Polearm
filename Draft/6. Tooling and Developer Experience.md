The tools and workflows used to create, configure and maintain a project have a significant influence on the quality of the development process. This chapter presents the techniques we used to make development more efficient, such as configurable resources, editor tooling and custom helper scripts. Examples like the encounter configuration workflow and the generation of animation frame data demonstrate how repetitive or error-prone tasks can be simplified through carefully designed tools as well as responsible use of AI in the project. These efforts reflect the same reasons which shaped the principles that guide the game's architecture, namely reducing unnecessary repetitive work and making complex systems easier to configure and extend.

## 6.1. To Configure Everything
---
In further accordance to our main development philosophy, almost every property of every object in Project Polearm is configurable, and even behavioral patterns can be oftentimes configured. This ranges from obvious things like player and enemy movement speed to even the decreasing factor of the jump velocity for aerial jumps. Almost every property which was functionally a constant is configurable, which in the code, oftentimes meant using the naming convention for constants for configurables, as well as the implied promise to not modify exported variables during runtime.

To name one of the most extreme examples of this agressive exporting practice, the `Hitbox` and `Hurtbox` collision components had a extra property exported just to set the collision layer or mask of the underlying Area3D, even though those properties already exported by Godot in the first place. This decision stems from the fact that Godot's collision layer and mask system can be confusing at times, as a tradeoff for their flexibility and power. Our collision components needs only one of them depending on their type, with the other bitmask set to zero. That along with custom exported variables always being at the top of the inspector, made the setup for the collision components far easier.

This, of course, lead to a large amount of exported variables in the editor. Those were organized into collapsable categories to maintain clarity. Exported variables were, for the most part, not centralized to improve code cleanliness, But for the player, some configurable variables, specifically many physics properties, are duplicated between states, which is why these were collected together in the `PlayerPhysics` structure. In hindsight, it might have been advantageous to create a centralized configuration file for all properties in the game, something akin to a more globalized variant of `PlayerPhysics`, as oftentimes during the design of the demo, we were had to look in adjacent systems for the location of an exported property.

### 6.1.1. `Encounter` and `Wave`
---
One prime example of configurability being used to its maximum are the `Encounter` and `Wave` structures. They are small POD resources with exported fields, but almost everything that can be said about an encouter can be found within these two classes.

Firstly, the structure of the two classes already mirror or research, where we stated that an encounter contains a wave of enemies (refer to the accompanying report for more details). An encounter defines the waves as well as the spawn points for the enemies, whereas a wave specifically defines which exact enemies will appear in which order where, as well as difficulty and other configurable data. The whole game object system shines here the most, as one must only fill out a simple array of the game object enum type of the specifc enemy the designer desires to design a whole wave, and repeat that for every wave in the encounter. 

The only thing `EnemyManager` now needs to starts an encounter is just the `Encounter` structure itself and an optional script. After this has been passed to the `beginEncounter()` function, everything plays out on its own. The designer now only has to pay attention to what exactly will trigger an encounter. In Project Polearm, this is done via the `EncounterTrigger`, a simple class which keeps track of two doors at the start and end of the encounter room, the trigger area for an encounter and the `Encounter` and `EncounterScript` itself. In Project Polearm, the `EncounterScript` only opens and closes the respective doors at the start and end of each encounter, but it might as well be extended to be able to do a large range of things, such as playing custom music, showing a cutscene and e.t.c.

In the enemy adjacent systems, configurability, extendability and flexibility were used to their maximum to create a system which was quick to set up and quick to iterate upon. To read more about how we improved developer experience with the `EncounterTrigger`, please refer to section 6.2.1..

### 6.1.2. Frame data
---
The `EntityFrameData` and its descendants might be the crown jewel of our philosophy of configurability. The feeling of an action in an action game is very important, and there are many things which can influence how the player percieves the game. From the moment from which an action may be cancelled, when an action may transition to the next, the certain frames in which the weapon is dangerous, or the point from which a queued input is accepted. These are not only "surface level" properties of an action, but also core to their behavior. This an incredible amount of properties which go with a single action, and these properties are not only one dimensional such as a simple flag, they have a second dimension: time. Not only was the fact that these timed events could be configured important to us, but also that the designer could easily and clearly configure them without touching a single line of code. How how should one design a system whose core behavior can be simply described through configuration?

This greatly increased the difficulty of the creation of the system, in fact, it was one of the systems which took the longest time to program and perfect during the first half year of development. We thought about many possible ways to implement such a system, such as the naive way to expose pairs of value and time for each state, but that would have gone against our configurability philosophy, and it also would not be very readable or performant at that. Atlas, through an external source, we came to a solution, something we had also seen from other action games, specifically fighting games: _Frame Data_.

Frame data describes the timing of all subactions within every move as a collection of properties mapped to the respective tick or frame of the animation. In fighting games, a move is typically split into phases: the startup, where the attack is being prepared and cannot hurt anyone yet, the active frames, in which the attack can actually hit, and the recovery, during which the character is vulnerable and cannot act freely. Beyond these phases, frame data also records at which points a move can be cancelled into another or when a buffered input is accepted. Players and designers use this data to reason about the game, as it describes precisely and deterministically what and when something happens.

To achieve such a system in Godot, we used the built-in animation system. `EntityFrameData` extends `AnimationPlayer` and is placed in each entity’s scene as a node. It holds an animation library, containing one animation for every animation the entity has, under the same name and with the same length. Instead of animating something like the skeleton of the character, we animate its properties. Designing timings thereby becomes the same activity as editing an animation: a key at 0.4 seconds which sets `_weaponActivate` to true means that the weapon is dangerous from that point onwards. The frame data is never played back, only sampled. Every property has a public getter of the same name, such as `weaponActivate(animationName, time)`. This function looks up the animation in the frame data library, finds the track of the property and retrieves the value at the requested time, which the action itself keeps track of with a variable advanced every tick. Setting the action properties has now become almost trivial, and the designer can perfectly pair up the properties of the action with its animation.

Using progress timer instead of the playhead of the real animation was a deliberate decision, since it keeps actions independent of the animation tree, which may blend or fade between several animations. It also keeps the results of each lookup deterministic, which is especially important for properties which influence the behavior of the action such as transitionability, something the normal skeletal animation player does not do or need.

This means actions ask what they should do instead of being told what to do. `nextAction()` asks whether the action is `transitionable`, `_processWeapon()` asks `weaponActivate` if it should enable or disable the weapon, `_processDirection()` uses the `rotationTracking()` speed and `_processSFX()` plays a sound effect defined by `sfx()`. All of this is implemented once, in the `EntityAction` base class, so every new state receives all of this behavior without a single line of code, whilst custom properties for a entity type could be implemented at any time. That is, in its most direct form, what _Configure Everything, Code Nothing_ means for us.

The greatest troubles came then with adding a new frame data animation for each new animation added to the project, which lead to the creation of the `EntityAnimationHelper` described in section 6.2.2.

## 6.2. Quality of Life
---
All this configurability was intended to improve the development experience, but there were also more sophisticated examples of this. We utilized in-editor helper scripts and/or helper functions during the development of the project, some being third party (see section 2.3.2.) and some also having been coded by us, with or without the help of AI assistence (always classified in the respective source files). These are some examples of these QOL-scripts in action:

### 6.2.1. `EncounterTrigger`
---
As described in section 6.1.1., spawn points for the encounter, including fixed spawn points for specific enemies, are also configurable. At the beginning, this was supposed to be done by designer, who would place a helper object in the scene, drag it around and manually copy its coordinates into the respective spawn point array. This proved to be very arduous, unintuitive and unclear immedeatly after this feature was first tested, and an alternative solution was conceived.

For the randomized spawn points, the most logical method was to be able to drag any `Node3D` into an exported slot, and to loop over all its children and set their global coordinates as the spawn points. But sadly, exported properties in Godot resources can't be `Node`s and during that time in development, the encounter data was still attached to the level data. Therefore some restructuring was undertaken for each `EncounterTrigger` to keep track of its own encounter data, so that the spawn point parent could be set on the `EncounterTrigger`, which would then automatically update the encounter in editor. This new restructuring and method for setting spawn points was more intuitive and provided us with a faster development and iteration time. Another positive side effect to this approach is that the designer could attach visual indicators to the spawn points, making the process even more streamlined.

But for fixed spawn points, the issue still remained open, and during design of the demo level, extensive configuration of fixed spawn points was to be used, which was not expected during development itself. Therefore, a similarly convenient method had to be devloped. It concluded in a very naively straightforward and consequently elegant solution, which was an extension of the previous practice: All spawn points are stored, yet again, in a spawn point parent, but they are numbered, the top level nodes simply carry the number of the wave, and the second level nodes, the proper spawn points themselves, carry the index of the enemy, which allowed for the same amount of flexibility, readability and clarity of the configuration of random spawn points. All these quality of life features made it possible to achive complex enemy placements with minimized time effort

### 6.2.2. `EntityAnimationHelper`
---
The `EntityAnimationHelper` is one of the densest helper scripts in the entire project, and even a very long script within the entire project itself. The development of this script was also a demonstration of collaboration between AI and humans, as the large majority of the script was written by AI (refer to `Entities/Entity/Utility/EntityAnimationHelper.gd` for more declaration), with many parts also having been edited or completely rewritten manually. What allowed for this style of heavy collaboration was the fact that the EntityAnimationHelper was designed to be completely isolated from the rest of the codebase. No other scripts reference anything it does, as the only thing the script does is modify resource files in editor. To be specific, it modifies the entities frame data and animations. The script is implemented to be so isolated, that it can delete itself during gameplay without anything being affected, which is what it does.

Motivation for the development of this helper script was the arduous process of manually adding frame data animations to the frame data animation library, which would all have to have  the same name as their corresponding animation. Furthermore, each frame data animation had to have the same length as its original animation, as well as a `_finished` flag set to true at the end the animation. At first we thought that the development of such a helper script would cause precious time that could have been utilized differently. But the we remembered that during early development, we had utilized AI to create a helper script which generated stairs in our gym environment. This we tried a similar, AI-based approach, and despite our initial scepticism, the result was almost immediately usable, with only minor modifications having to be undertaken. The script was even extended over time to encompass more QOL-features such as automatically updating the length of animations when those have been updated or completely delete any animations which could not be found in the current animation library, common occurences when we were still importing and modifying animations.

Towards the end of development, the issue of some animations containing a scaling component, which was caused by the animation importation process, which the _Jolt_ physics library functionally ignored, but still logged an error about, was also raised in a discussion with our main overseeing teacher, Mr. Schneider. We decided that it would be best to remove those alltogether, than writing a disclaimer which declared that the scaling was not detrimental to the execution to the game and letting _Jolt_ fill up the terminal with error messages. As the animation library had already been an exported component in the script, having AI setup a function which deletes all animation tracks containing a scaling animation was trivial. The change was applied, and the logs of the game were finally free from error messages.

This script came to be utilized for all six entities in the game, and at the end, time spent developing this helper script had proven itself well worth it, saving us time and effort for more crucial parts of the project.
