## 5.1. Boot sequence
---
What fits better than starting the section on the procedures and algorithms used in Project Polearm with how the game even boots itself. As suggested by section 4.1., Project Polearm is designed in such a way that starting the game does not even mandate the loading of any enemies, the game world or the player for that matter. This design decision was made to increase the flexibility of the game, as it becomes possible with only configuration and code to choose where the game loads into and how the game loads into the place. In theory, it is even possible to load Project Polearm into a completely different game which shares none of the mechanics with the demo without issue. This, in turn, would theoretically simplify the our work if we would decide to add more levels.

## 5.2. Entity action selection
---
There are multiple ways of implementing state switching inside of a finite state machine. One common way is to explicitly define which state may transition to which other, and store this transition information somewhere. Although this does work, it is very cumbersome to do and to debug, as workload increases quadratically to the number of states. The player of Project Polearm contains, as mentioned, 26 states, which would mean 676 transitions to potentially configure and debug.

This was out of the question. Although some state transitions were explicitly defined in code alongside transitions, the vast majority of state transitions were handled through a priority system. An action with a higher priority will be taken first as a candidate for state transition.

In Project Polearm, states and actions are used to refer to the same thing, the state of a finite state machine which defines the behavior of the system once active. Actions are specifically used with entities, as this makes sense in that specifc context. Furthermore, inputs and actions refer to similar concepts within an entity, whereas an input is simply an idenfication for an abstract input event, which always maps to a specific action or a chain thereof.

## 5.3. From Attacking to Damage
---
Project Polearm defines two structures, which are core to the damage system. These are the `Hitbox` and `Hurtbox`. Hitboxes are active and scan for the passive hurtboxes. Hurtboxes in turn leave a implementation function open to the developer to determine the behavior after a hit. Both hit- and hurtboxes use the default collision layer and detection system provided by Godot's `Area3D` node instead of reinventing the wheel.

The `Hitbox` is highly decoupled from the rest of the game's systems, as it knows of no other system except for the Hurtboxes, and even then does it not care what specific type of hurtbox it encountered. The Hurtboxes on the other hand are specifically implemented for each entity which wants to use one to encompass all possible custom behavior. Here, all the `EntityHurtbox` needs to do is to tell the entity's resource container to take damage, and it stops caring about the exact implementation.

The entire Hit- and Hurtbox system is so decoupled, that it is even possible to delete the components from the entity and have it still work, albeit at the price of losing the functionality which these systems intend to provide. This was demonstrated when we first implemented taking damage. What could have been an arduous process of linking systems became adding a scene to the Player and have it call the proper function, and thus, taking damage just worked.

The reason why hit- and hurtboxes are not a solid body or just the collision shape of the character's physics body is to enable as much flexibility as possible. If the designer wanted that to be the case, this would just have to be configured, but leaving this open creates a lot of possibilities, f.e. by being able to adjust hit- and hurtbox size for a different gameplay feeling without being coupled to the physics simulation of the character.

## 5.4. Enemy Role Assignment
---
The `EnemyManager` has multiple responsibilities. In a nutshell, these are:
- Ticking enemy AI
- Spawning enemies
- Assigning enemy roles
Whereas the assigned roles are pushed to the enemy AI, also called enemy controller, through the tick function, where the assigned role and other data are packed in to a structure. The algorithm which allocates these roles is also rather lengthy and advanced.

This is due to the large amount of configurability of the encounter. Even aside from enemy spawning behavior, the designer can configure the difficulty of the current wave by setting the `MAX_ROLE_DIFFICULTY` property in `Wave`. This difficulty works as a sort of point system, which is calculated by adding up the difficulty score of the roles of all enemies currently active. This property is always respected as best as possible by the Enemy Manager and used to its limit. The respective enemy AIs can then be assigned the roles that they can take, although it is up to the AI implementation itself to resepct the roles that it has been assigned to.

Now with the newly aquired role, it becomes the responsibility of the enemy controller what to make of it. Roles are only something abstract, and the concrete implementation in the enemy might differ. For example, the `ArcherController` starts the preparation routine for a shot when it recieves the role shooter, and `SoliderController` picks a flanking target at a certain, configurable radius around the player and sets that as the new target for the enemy.

The enemy manager allows for enemies to not being able to take on all defined roles and respects this fact for all role assignments, which is also the case for enemies in Project Polearm. This gives the designer and enemy AI implementation more flexibility. A concious decision can be made for which roles to split, which roles to describe using the same tag and how different enemies might behave differently even though they have the same role.

## 5.5. `FloatingBody`
---
The algorithm used in `FloatingBody` is one of the most advanced single algorithms in the entire project. It is a `CharacterBody3D` that does not stand on the ground but floats slightly above it. The body collider is shortened by `BODY_COLLIDER_FLOATING_HEIGHT`, so the lower part of the character is covered by a sphere cast and rays instead of the collider itself. This allows the body to walk over small steps and slopes without catching on edges.

This works by approximating the bump in front of the player as a slope whilst moving. And thus, during contiguous movement, it appears to be smooth. If stopping on a step, then the body will slowly move the character up or down to the actual ground height.

Every tick is split into three stages:
- Collision processing
- Velocity calculation
- Movement

The `FloatingBody` does not simulate physics realistically. For example, to allow the player to jump without any weird behavior such as sluggish movement in proximity to the ground or clipping into the ground due to the reduced collider size, the floating body uses a "physics" mode, where the collider is set to full size to allow Godot's physics simulation to take over.
