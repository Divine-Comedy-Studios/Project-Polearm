A clean architecture does not emerge by accident. It is the result of decisions made in early development about principles which shall guide the software's programming. This chapter presents the central philosophies and design goals behind Project Polearm, including configurability, modularity, extensibility and the use of established and uniquely modified programming paradigms and design patterns. The philosophies are not abstract principles and empty jargon, as they have directly influenced our development process from the macro- to the microscopic level. Together, they establish the reasoning behind the architecture explored in following chapters and demonstrate our intention to keep the codebase flexible, consistent and comprehensible.

## 3.1. _"Configure Everything, Code Nothing"_
---
This is our core philosophy for the project since the beginning, and almost all systems and code strive to align themselves with this philosophy. The reasoning behind it stems from the strict time limit of the matura project and our inexperience working on larger projects. To avoid unorganized code, it is better to write less code in the first place. If systems were not designed in a way to be actively called, but to be passively configured, a lot of time that would have been spent coding could be saved. We saw a lot of potential in this thinking especially in action games, especially since we believe that Hack-and-Slash games are incredibly data intensive, as one action can have many variants. For example, an action game may have many attacks, but they remain attacks, and their behavior can potentially be encompassed with the same few sets of functions, but executed under a different set of conditions. Instead of coding these conditions, we strived to configure them.

Another philosophy central to the development of Project-Polearm is modularity for subsystems. This effectively also plays into the _"Configure Everything, Code Nothing"_ philosophy. If subsystems are truly modular, they can simply be added into the scene, configured and instantly work, even in the presence of and/or with other systems. Furthermore, for larger systems, extendability is another design goal which we paid extensive attention to. This also meant more upfront development time, as systems had to be engineered in such a way that they are ready for as many future changes as possible without massive changes in existing API, and such that they are able to accept modular subsystems.

This also leads into one of our major philosophies in development, which is the be ready for the future. Systems should always be ready to accept future changes in the future. This means that all code written is done so in anticipation of planned features, and that the integration of those, even though not implemented, is already respected in the code and can be simply added without further question, again, as part of our extendability philosophy. But this also meant that this philosophy was one which carried great tradeoffs with it, as this was also one of the contributors to a long development time, where in theory, it would pay off in the end.

The goal of pursuing these philosophies had a few practical reasons. Firstly, consistency and good practice were certainly goals this codebase strives to achieve, since if every system was made with the same mindset, they would all behave in a similar fashion. On the other hand, the cleaner the codebase, the easier it is to work with it in the future, as long as one is willing to pay the price upfront.

## 3.2. Paradigms
---
Our primary design philosophy heavily implies the usage of a certain programming paradigm, namely data-driven programming. This means that many systems are comprised of two parts, namely the behavioral part and the configurational part. The behavioral part defines all features of the system. Whereas in other codebases, these might be exposed as an API and used exclusively as such, Project Polearm chooses to also expose configurable structures in the editor, and have the the system itself or other systems utilizing the system interpret the configuration and call the API functions for the programmer. 

In practice, this meant that many systems were oftentimes extremely centralized, or at least, locally centralized. Therefore, the game contains global state. The upfront development time of such systems took longer than what would have taken to create their non-centralized and solely API-based equivalents. Most systems contained such an API for some certain use cases, and the configuration data structure and its interpretation also had to be created in a well-architectured, non-invasive and extendable way, which should work for the majority of use cases. If done so correctly, this oftentimes lead to almost no code when using the system in other parts of the project. More concrete examples of this philosophy in action will be demonstrated in Chapter 5.

Since we are working in a Game Engine, we also had to work within the philosophies of that Engine. Godot is object oriented, and extremely so at that. Godot uses composition by `Nodes` to build its world, as many objects in Godot are a node. Nodes describe scenes and behavior. One node may contain multiple nodes and build to so called _scene tree_, and every node inherits from another, simpler one. To give an example, a `Node3D` extends the basic `Node` by introducing a field describing its transformation in 3D space, which a `Node` does not have. Every other Node which needs to describe its transformation in 3D space will directly inherit in some way from `Node3D`, f.e. `CollisionShape3D`. This node is placed as a child in the scene tree of a node which inherits `CollisionObject3D`, defining a specific behavior during coillision with its collision shape. In turn, `CollisionObject3D` also inherits from `Node3D.

We also worked within Godot's design philosophy, and it came with some advantages and limitations. Such a node system was the cornerstone supporting the modularity and extendability principles, as commonly reused parts of a scene tree can be saved as a separated scene, which can than be instantiated to create copies of itself when needed This facilitates extendability, but careful consideration still had to be taken to keep clean architecture.

Then again, it should not be undermined that one also has to consider how this system limits the developer, as all systems do. Communicating nodes could exist at varying depth levels of the tree, which made the process of setting up a path of connection in an architectually clean way a difficult one. Communication between systems was not straight forward. Godot provides multiple solutions to the issue, and leaves to programmer to decide, for better or worse, which one to pick. We were left wishing for other solutions, though our concerns were never strong enough to force us to start searching for alternatives.

## 3.3. Avoiding Signals
---
One of these solutions are the _Signals_. Signals are an integral part of Godot's design and the documentation encourages their usage. But all hand-authored code in Project Polearm uses signals extremely sparingly and in very localized situations. Our signals even rarely cross multiple nodes. But If we already established that communication between nodes is a problem, then why did we avoid such an obvious solution to our issue?

In early development, a concept about a signal bus was raised. It was supposed to be a global structure which accepts signals from any source and sends them to whatever target wants to recieve them. The idea did not survive long until we agreed that his was not the way to go. Signal busses are a popular paradigm in the Godot community (==🔴CITE SOURCE!!!)==, so why this negative reaction from us? Firstly, the sheer amount of systems which will need to communicate within a game is huge, and the signal bus is an obvious and easy answer to this problem, too easy in fact. We sensed that it might become a default solution to every complicated architectual problem we come across, and instead of thinking about a clever way to resolve this issue, a new signal is simply added into the singal bus. This endless cycle continues until we have a massive source file, maybe even the longest file in the entire project, and nobody would know anymore which signal connects which to what.

A proper solution to global state should be ugly. It should be direct. The signal bus hides a certain level of directness, which would be achieved with a reference to a global object behind a apparently clean language feature, encouraged by the documentation and the community. People say that signals decouple systems from each other, and decoupling is something good. But many times, even with a signal bus, the systems remain coupled. If the player wants to play a sound, then the global sound system and the player become inherently coupled. Given two systems which are structurally coupled and in need of knowledge about each others existance, if a signal bus were to be used naively to elevate this issue, than the coupling would become simply functional, where one system relies on the other system to doing something. One thinks the problem is resolved, where the coupling really just took on a different form, and even worse, the coupling becomes hidden and indirect.

Therefore, coupling, if it happens, should be direct, and the solution to global state should be ugly. Because if that is the case, every time a global object is used in a way where coupling happens, it will feel akward or wrong. Only then can the developer incentivize themselves to limit global state as much as possible, and the code comes out the cleanest. Signal busses could even incentivize coupling in an ironic way. If two systems risk coupling themselves, and a solution is needed, one could either resort to the easy way out and add a signal to the signal bus, and the systems become indirectly coupled. 

This also explains our use cases for signals. Signals are not inherently unclean, we must simply use them in a way that we find to be clean. In the cases mentioned, signals are either the only way to achieve a goal or the cleanest way to do that, for example to detect UI-buttons. As the use case is confined to that specific menu the button is in, and the button only communicates with its manager and nothing else, we deemed this use case and other similar cases to be clean and perfectly acceptable.

### 3.4.2. Global State
---
Godot provides multiple ways to realize global state. The Godot documentation encourages the use of _Autoloads_, which we initially tried, but quickly decided against the use thereof, as _Autoloads_ have the same effect as setting all members of the class to be static members, therefore polluting the global namespace with the name of the class. Furthermore, _Autoloads_ are unconditionally always initialized, unless removed inside of a menu, which could break further dependencies. This means that errors in a globally loaded system will always be present, even if the code to be currently tested does not require that specific system. Therefore, we went with a unique approach, which works like:

```
# Globals.gd

class_name Globals

static var fooSystem : FooSystem = null


# FooSystem.gd

class_name FooSystem

func _ready() -> void:
	if Globals.fooSystem != null:
		# Throw an error, etc.

		return
	
	Globals.fooSystem = this
	
	# Other initialization steps...

```

This means, that in order to initialize a global system, a node has to be explicitly placed in the scene tree in order to be initialized, which makes it also follow Godot's usual initialization logic and order. If the system is not used in a particular testing scenario, the field in globals will simply remain `null` and any other bugs in the system will not influence the tests. Furthermore, if a system was not fully implemented and still contained syntax errors, its corresponding line in the Globals file could be simply commented out. All non-third-party global systems in the game use this exact pattern.

This also means that these global systems are not truly global, as their core functionality is still local. If there were no assert checking for a duplicate of the system in the global registry, the system could work all on its own, given its dependency to other global systems are resolved. The only truly global object in Project Polearm is the `Globals` registry.

### 3.4.3. State Machine
---
State machines also proved to be a very widely used pattern in Project-Polearm. Many things in a game can be described using a state machine, and it was the holy grail, so to say, to our three philosophies of _Configure Everything, Code Nothing_, _modularity_ and _extendability_. State Machines in the project provided the developer with a large amount of freedom configurability as well as an extensive API, but a very limited way to where each state may be extended, which was achieved, for example, via the use of the _Template Method_ pattern. This way, we hoped that the creation of new states for the state machine can be trivialized, as with the proper design, each state could be made responsible for a single action only, greatly simplifying its code.

Furthermore, the freedom of configuration was achieved by programming the State Machine with the design of Godot in mind. The states are nodes in the scene tree instead of being raw pieces of code. They are children of the state machine and their properties as a state of the state machine could therefore be simply configured in editor. Managing states was therefore done by leveraging what Godot has provided the developer, instead of using a custom system, greatly simplifying the code. Furthermore, the basic state machine uses a sort of "inverted" Template Method pattern, it does nothing on its own, as it does not use the Godot built-in functions, instead, it chooses to let the developer call its functions later on in an inherited class, for maximum extendability and flexibility.

Due to its good synergy with our three design philosophies as well as being a very versatile pattern, state machines are in every part of Project-Polarm. Just to give a broad overview, the Entities are state machines, the menus are state machines and the entire core processing of the game happens in a state machine. ## 3.4.4. _Dataset_
---
The dataset is a pattern which is widely used across the entire project, but calling it a pattern in itself would be slightly misleading. A dataset carries no functionality, it is simply a dictionary of plain-old-data to a type enum or an equivalent identifcation structure. 

```
# FooData.gd

class_name FooData
extends Resource

enum Type {
	# Some types of Foo...
}

@export var FOO : bool = false
@export var BAR : int = 0
@export var FOO_BAR : Vector3 = Vector3.ZERO


# FooDataset.gd

class_name FooDataset
extends Resource

@export var DATASET : Dictionary [FooData.Type, FooData]

```

But the dataset was incredibly important to execute on the _Configure Everything_ part of our core philosophy, as these datasets were oftentimes exported alongside a system to define the set of objects it should act on and the way it should act on the specific object.

For example, the sound system exports a sound dataset to define all sounds and their configuration that the game needs. Playing a sound becomes as simple as simply requesting a type of sound to be played, and the sound system automatically uses the sound from the dataset entry alongside its configuration. Changing out the sound for something else becomes trivial. Otherwise, a call to the playSound function would require hard-coding the path to a sound file and adding a lengthy list of settings. Due to its simpleness and universality, this pattern is used in other core components of the game such as game object management, encounter configuration, stage loading, combos and more.
