Before examining the code itself, it is important to understand how the project is organized. This chapter introduces the file structure of Project Polearm, the purpose of its directories and describes the conventions established throughout development. By grouping related systems, separating shared resources from system-specific implementations and following consistent naming and structural conventions, we sought to make the project understandable and maintainable even as it grew in complexity, as cleanliness is not only important in code, but also where the code resides.

## 2.1. Files
---
Within Project-Polearm, the majority of the files are either of the extensions `.gd`, `.cs`, `.tscn`. These contain the code and scene data needed by Godot to run the game. The code for the game is found in `.gd` and `.cs` files, whereas `.tscn` and occasionally `.scn` describe scene files. `.tscn` stores its data in a human-readable and editable text format based on the INI format, and `.scn` stores its data in a binary format, which is exclusively used for scenes containing large amounts of data. One can also encounter `.tres` (text resource) and `.res` (resource) files within the project, which denotes other data which the Godot needs to run the game. `.gdshader` files denote shader files in Godot's custom shader language.

One can also find an assortment of files which contain the assets of the game. 3D Models are exclusively stored in the GLTF format with the extension `.glb`. Textures are most commonly stored as `.png` files and `.jpeg` files. Godot resource files may also be found here.

Other file types can also be found throughout the project. Unless explicitly denoted otherwise, these contain metadata used by Godot or configuration information for either Godot, .NET or IDEs utilized for editing the source code.

## 2.2. Conventions
---
The project uses a set of enforced conventions for its code and files to promote navigability, consistency and good practice. They are documented in `Common/Templates/Convention.gd`. This convention fully defines a rigid structure and way of organizing code for all long code files, as well as standardized naming conventions for almost every language feature and pattern used.

Furthermore, we have also orally agreed upon a convention for all file and directory names at the start of development, which simply amounts to naming all files and directories which are not generated automatically in pascal case.

Although the naming conventions are enforced throughout most parts of the project, some conventions were enforced with some leniency so to allow for developer flexibility, as conventions are only good aslong as they promote their stated goals, which is navigability, consistency and good practice. The conventions were not enforced for their own sake.

## 2.3. Directories
---
All directories in the project were named to be as self explainatory as possible. The entire project encompasses below directories:
- `Assets`
- `addons`
- `Common`
- `Components`
- `Docs`
- `Interfaces`
- `Stages`
- `Entities`
- `Objects`
- `Systems`
- `Core`

We organized our directories as such to best describe their contents as well as their association and dependencies. A directory usually contains source and scene files which belong to the same system, or a grouping of systems which stands on its own pillar within the project.

The files in the root directory of the project, which are of note, are the core project configuration file `project.godot` and `README.md`, a short introduction to the demo alongside explanations for core game mechanics. The `Docs` folder contains assets used in the `README.md` file and is not relevant for the rest of the project.

Below is a summary of all other directories within Project Polearm and an explanation of their contents in alphabetic order:

### 2.3.1 `Assets`
---
The `Assets` directory contains the majority of the game's visual and audio assets, including 3D models, textures, materials, animations, sound effects, music as well as their metadata. The subdirectory under `Assets` directly categorize the type of assets contained within. Within those, assets are either sorted by their functionality, their associated system and/or the source ==🔴(provider??? whats a better word)== of the assets, allowing them to be located and referenced relatively easily.

It is important to note that the assets in this directory consist of external assets. That means that they do not directly influence anything about the execution of the game. Other assets, spefically game data, like animation frame data or asset datasets, which are crucial to the behavior of the game, are stored alongside their respective systems and entities.

The directories are named to be self explainatory and will therefore not be explained further.

### 2.3.2. `addons`
---
This directory contains all Godot plugins used throughout the games development. As mentioned, only `PhantomCamera`, found in the folder of the same name, is necessary for the game's execution, but other extensions were kept for completeness sake.

The plugins were installed through Godot's built-in asset store, which downloads them into this specific directory. The name of the directory uses Godot's own convention, which we did not enforce our own onto, as that may cause issues and inconveniences. Therefore it is the only directory in the project, created by us, which does not conform to our naming convention.

These are all addons used in the project and how we utilized them in Project-Polearm:

| **Extension / directory name** | **Functionality**                             | **Reason for utilization**                                                                                                                                                                                                           | **Runtime dependency**                      |
| ------------------------------ | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------- |
| **`anim_player_refactor`**     | Edit Godot scene paths within animations      | Godot usually imports models grouped alongside their skeleton and animations, which we separated ==🔴(see section XXX)==. Therefore, all animation paths become invalid and must be reset                                            | No, editor plugin                           |
| **`debug_draw_3d`**            | Draw simple, geometrical shapes for debugging | This plugin was used during development to display 3D-debugging information, f.e. mainly for the inspection of vectors                                                                                                               | Runtime Plugin, no release build dependency |
| **`phantom_camera`**           | Ready-to-go camera library for Godot          | Godot cameras only implement basic features, with the rest having to be implemented by the developer. Phantom Camera implements functionality useful for most games, like following, smooth camera movement, camera collision e.t.c. | Runtime plugin, release build dependency    |

### 2.3.3. `Common`
---
`Common` is the place for everything which does not belong to a single system, but is needed by several of them. What separates it from `Components` is that nothing in here is meant to be dropped into a scene and configured on its own. The code is either supposed to be extended, called from elsewhere, or only ever run inside the editor.

The most important part is the `StateMachine` folder, which holds the generic finite state machine and its base state. Nearly everything in the game which has to switch between modes, from the application itself down to the individual actions of an entity, is built on these two classes (see section 3.3.3). Next to it, `Utility` contains `PPUtil`, a collection of constants, enumerations and math helpers, like measuring the horizontal length of a vector. As the project uses both GDScript and C#, it exists in two versions, `Utility.gd` and `Utility.cs`, so that neither language has to reach across the language boundary for simple tasks.

The `Camera` folder contains `SceneCamera`, the main camera of the game. As PhantomCamera operates via a main camera host and sub-cameras, whereas the sub-cameras may freely decide the transformation of the camera which the main camera host manages (see section XXX), the host is kept as a scene of its own, which also carries the post-processing quad of the game's visual style. The cameras were deliberately split into subscenes from the `Visuals` system to promote modularity and potentially swappable cameras in the future. `ShaderCamera`, an experimental camera using a different shader, still lies next to it, but is not used by the game ==🔴(keep or delete?)==.

Everything responsible for the look of the game is found in `Shader`. `Industrial` contains the stylized material shader, the full-screen post-processing shader together with its `PostQuad` scene, and the master style resource which all of them read from. `Reference` keeps the toon shaders which preceded it, and `Textures` holds the textures the shaders need. A small editor script in `Tools` converts existing materials to the toon shader.

Finally, `Templates` and `Tools` serve the developer rather than the game. `Templates` contains `Convention`, where the code conventions of the project are written down (see section 2.2), as well as a script template for new player states. `Tools` holds three scripts that only run inside the editor: a generator for staircases built from CSG nodes, `LevelMesh`, which applies the style of one master resource to every mesh of a level, and an import script which sets the metallic value of imported materials to zero. The staircase generator was written with the help of generative AI ==🔴(see section XXX, AI declaration)==.

### 2.3.4. `Components`
---
Components are the practical result of our _"Configure Everything, Code Nothing"_ philosophy (see section 3.1). Each one is a small, self-contained building block, which can be added to a scene, configured through its exported variables and then simply works. To keep it that way, components know nothing about the entities, systems or stages which use them, and depend on nothing but `Common`.

| **Directory**   | **What it does**                                                                                                                             | **Used by**                      |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| `Collision`     | `Hitbox` and `Hurtbox` for dealing and receiving damage, and `HitboxData`, the resource describing a single hit (see section XXX)           | Weapons, entities, kill zones    |
| `EventTrigger`  | An area which reacts to bodies of configurable collision layers entering it                                                                  | Encounter triggers               |
| `FloatingBody`  | The character controller of the game, written in C#                                                                                          | All entities                     |
| `Interaction`   | An `Interactor` and `Interactable` pair for interactions with objects ==🔴(unused, keep or delete?)==                                        | Nothing                          |
| `LedgeStopper`  | Keeps an entity from walking off ledges                                                                                                      | The player                       |
| `Miscellaneous` | `RemoteChild`, a node which follows the global position of another node without being its child                                              | The player camera                |
| `NumericResource` | `ValueResource` and `IntegerResource`, which hold a value and its maximum and notify other objects when it changes                         | Health, energy and other values  |
| `ValueBar`      | Bars which display a `ValueResource`, either floating above an entity in the world (`ValueBarFloating`) or on the interface (`ValueBarUI`)  | Player and enemies               |

Although most components are only a few dozen lines long, `FloatingBody` is a clear exception. Its code is split into three files, one for the node itself, one for the functions other code calls, and one for the physics calculations, and its development is described in section 8.2.1.

### 2.3.5. `Core`
---
`Core` contains everything that controls the large-scale flow of the game, which is starting, loading, running, pausing and quitting. These parts are not organized as one large piece of code, but as state machines nested into each other (see section XXX).

The outermost layer is `Main`, which contains the scene Godot loads first. Its `Boot` scene starts the game, and its `States` folder holds the states between which the game moves on the application level: the main menu, the game itself and quitting. Inside the game state lives `Game`, a second state machine which runs while the game is actually played. Its `World` state loads the stage and the player and handles game over and restarts, while `PauseMenu` and `DeathScreen` connect the menus found in `Interfaces` to the state machine.

Both layers are built on the same base. `AppStateMachine` extends the state machine of `Common` by the requirement of a loading state, which the machine enters whenever its next state is not ready yet, and it is the reason why both `Main` and `Game` have their own `Loading` folder with a loading screen. The boot sequence through all of these directories is described in section XXX.

### 2.3.6. `Entities`
---
Entities are the characters of the game, which are the player and all enemies. Instead of giving each of them its own implementation, they all inherit from a shared base, and extend it with what makes them different:

```
Entity
├── Player
└── BasicEnemy
    ├── Solider   (variants: HeavySolider, Ninja)
    └── Archer    (variants: ChainArcher, HeavyArcher)
```

`Entity` holds everything every character needs: the action state machine, the animation and frame data, the receiving of hits, the combo system and the resources like health. `Player` adds to this the input handling, its camera and its visual elements, while `BasicEnemy` adds the controller, which decides what an enemy wants to do, and the actions every enemy shares. `Solider` and `Archer` are the two enemy types of the demo, a melee and a ranged fighter. The variants are further enemies derived from them, such as the armored `HeavySolider`.

Every entity directory is organized in the same way. `Actions` contains the action manager and, in `States`, one script per action the entity can perform. `Animation` contains the animation helpers and `Controller` the enemy behavior. The difference between `Data` and `Resources` is worth remembering, as it applies to the entire project: `Data` contains the scripts which define _what_ can be configured, whereas `Resources` contains the actual configured instances. The combos of the player, for example, are `Resources`, whereas the structure of a combo is `Data`.

### 2.3.7. `Interfaces`
---
Everything the player clicks on, reads or navigates through in menus is located in `Interfaces`. The menus are built on `InterfaceStateMachine`, a state machine of their own with a small input manager, which is independent of the application's state machine in `Core`. That way, the same menu machinery can be used by the main menu, the pause screen and the death screen alike.

The menus themselves are found in `Menus`. These are the main menu with its save selection and quit confirmation, the pause menu, the death menu, the options with their audio, game, key mapping and video pages, and the save menu, as well as a `Button` which is shared between them. All of them use the single theme found in `Themes`.

The game is also translated. The `Language` directory contains one table of all texts of the game and the translation files generated from it for German, English, Spanish, French, Italian, Japanese and Chinese.

### 2.3.8. `Objects`
---
Objects are what is placed into the game world, but is neither alive like an entity, nor a general building block like a component.

The `Weapons` directory is the largest part. `Weapon` is the base of everything which can hurt, and it is extended by the weapons of the player and the `Solider` enemies, among them the `Hammer` and the `Scimitar`. `Projectile` extends it again with a handle and physics of its own and is the base of the `Arrow` and the `HomingMissile`, which are spawned while the game is running instead of being placed into a scene beforehand (see section XXX).

Besides that, there is the `Door`, which blocks the way as a force field while it is active and can be switched off through signals, and the `KillZone`, an area which damages everything inside of it and extends the `Hitbox` component. The `SavePoint` directory is currently empty ==🔴(delete or explain)==.

### 2.3.9. `Stages`
---
A stage is a scene which the game can load as its world, consisting of the level geometry, doors and enemy encounters. The base script of all stages is `Stage.gd`, directly in this directory. It defines the stage types and holds the stage's configuration. That configuration is described in `Data`, where `StageData` holds, for example, where the player spawns, and `StageDataset` assigns each stage type its scene.

The only level which is part of the demo is `Level_1`, found in `Levels`, together with `Encounter.gd`, which describes the script of its encounters. The other directories contain stages that were not made for the player, but for us. `Documentation` holds `Gym`, the open testing area used for player mechanics and enemy encounters throughout development (see section 8.1), as well as `Museum` and `Zoo` ==🔴(describe)==. `Test` contains small scenes used to try out individual systems in isolation, like audio, pooling, interfaces, shaders and value bars.

### 2.3.10. `Systems`
---
Systems exist exactly once per game, and provide services which many other parts depend on. Most of them follow the same rules: they are nodes in a scene, they register themselves in `Globals` when the game starts, and they refuse to do so a second time, which makes them singletons (see section 3.3.5). `Globals` itself is the script lying directly in the root of this directory, and holds the references to all systems.

| **Directory**   | **Responsibility**                                                                                   | **Found in `Globals` as**          |
| --------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `Audio`         | Playing music (`AudioManager`) and sound effects at positions in the world (`SFX`), with their datasets | `audioManager`, `sfxManager`       |
| `EnemyManager`  | Managing all enemies of a fight: encounters, waves, trigger and the information enemies receive about the player (`Perception`) | `enemyManager`                     |
| `GameObject`    | Spawning and pooling of objects like the player, enemies and projectiles, driven by one dataset      | `gameObjectManager`                |
| `SaveUility`    | Saving and loading of save data                                                                      | `saveUtility`                      |
| `Settings`      | Storing and applying the game's settings                                                             | `settingsManager`                  |
| `Visuals`       | Holding the camera and world environment of the game                                                 | `visuals`                          |

Two of these deserve more attention than a table row can give. `GameObject` is how nearly everything dynamic enters the game, as it creates objects from a single dataset and recycles them instead of deleting them (see section XXX). The `EnemyManager` was the most difficult system to get right, and its algorithm and development are discussed in section 8.2.2. The remaining systems, namely `Audio`, `SaveUility` and `Settings`, are comparatively small and are therefore not explained any further.
