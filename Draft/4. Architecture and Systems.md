Now, we examine the architecture of Project Polearm through major systems that make up the game. It moves from the overall structure of the application to the individual systems for entities, combat, state machines and shared functionality. Through architectural diagrams and explanations of their relationships, this chapter demonstrates how a comparatively large collection of interactions can remain organized through managed communication and distribution of resposibility. Systems abstracted and dependencies are kept deliberate to avoid tight coupling of unrelated parts of the game.

## 4.1. Architectural Overview
---
The architecture of the game can be roughly divided into three layers. The first is the _core_, which decides the current state of the game (booting, in the main menu, in the game). The second is a set of global systems that live as long as the application or the world does, depending on their location. The third is the _interface_ layer, which holds all menus. This subchapter explores these three layers.

The core consists of two nested state machines, where `Main` is the top level machine. On start, the application enters `Boot`, which is a short splash state where the settings are applied. It then moves on to the main menu, and from there into the game or out of the application.

The `GameState` does not hold the game itself, but loads it dynamically on request. The loaded `Game` is again a state machine, with the states `DeathMenuState`, `PauseMenuState` and `World`. This separation stems from not every state the game is in needing to be loaded at the same time. Pausing or dying can only occur during gameplay, which is excludes the possibility of needing, the main menu loaded and vice versa. 

Both machines own their own loading screen. When a state is not ready yet, for example because its scene is still loading in the background, the machine first switches to its loading screen and enters the requested state afterwards. Both mechanisms above are explained further in section 5.1..

Continuing into the next layer of the game, most of the functionality that is not specific to a single state lives in global systems. Each of them has one responsibility:
- `SettingsManager`, which loads, stores and applies all settings
- `AudioManager` and `SFXManager`, which handle music and sound effects respectively. The `SFXManager` uses the sound effect data to from the `AudioManager`, and can therefore be understood as a subsystem of the AudioManager
- `Visuals`, which handles the global visual settings
- `GameObjectManager`, which creates and recycles all non-static game objects through pools
- `EnemyManager`, which manages the enemies of an encounter. It spawns them through the `GameObjectManager`and assigns roles to their AIs

The systems are owned by the part of the core whose lifetime they share. The settings, audio and visuals belong to `Boot`, as they are set up once at the start. The `GameObjectManager`, the `EnemyManager` and the `SFXManager` belong to the `World`, so they are only alive while a game is running, again, as these are only needed whilst the player is in the game world.

To avoid passing references to every node that needs them, every system registers itself in the `Globals` registry as soon as it is ready. Any other part of the game can then reach them from there.

## 4.2. `GameObjectManager`
---
In Project Polearm, all non-static objects are handled by the `GameObjectManager` and its subsystems. This ranges from enemies, projectiles up to even the player, as demonstrated in section 4.1.. The `GameObjectManager` is responsible for managing all `GameObjectPool`s, which exists once per entity type. The `GameObjectPool` themselves handle the actual pooling, spawning and death of its managed game objects.

This on the one hand, is an opimization pattern. Normally, one might manually instantiate a scene into the world and delete it when the game object is dead. But this requires reinstantiating the object every time one needs it, which could possibly cause sudden lag-spikes during execution. It would be far more efficient to store dead game objects somewhere where they can simply be retried, resetted instantly reused. This means, that f.e. if the game will ever only show 8 enemies of the same type on screen at one, that in total, only 8 unique instances of the enemy will ever exist. This is a common optimization used in many games. The drawback is the slight amount of boilerplate introduced to implement resetting logic, which for us was trivial.

On the other hand, this allowed us to significanly simplify the process of spawning anything into the game world. One must only configure the `GameObjectDataset` once in the global `GameObjectManager`, and it becomes possible to simply use its corresponding enum value to spawn the entity. The developer only has to state once where the entity scene is and of which type the entity belongs to, and spawning it anywhere within the game code becomes as simple as `Globals.gameObjectManager.spawn(GameObject.Type.someGameObject)`. This also makes it trivial to add new types of entities or swap out old entities with something else.

Furthermore, to increase flexibility, one can also pass a payload to the spawning function. The `GameObjectManager` does not provide any default behavior upon spawning, thus the developer can decide precisely what data they want to pass onto the object. This payload is used to carry anything from a simple `Transform3D` up until the configuration data for a whole projectile.

The Game Object system also only cares about the spawning and despawning of the entities, it does not interfere with the ticking or any other aspect of its managed objects. This decouples the actual implementation of the object from the interface of it and the game object system and frees the developers mind from having to think about resource management, as the system takes care of object lifetimes for the developer, who now only has to decide when to spawn something in.

## 4.3. Entities
---
The entity, i.e. the structure which lies at the base of the player and all enemies in Project Polearm is a complex system consisting of multiple components communicating to create a single, coherent character. The entity in Project Polearm is designed using the _Model View Controller_ paradigm.

The model is the heart of every entity. It defines the behavior and connects all components together. The core of the entity controller is a state machine, the `EntityActionManager` and its children. It manages the transition between states and acts as a registry for all components, which are in turn provided to the states, so that the currently active one can determine the current behavior.

To take the core state machine of the player as an example. It contains 26 states. All states act independently from each other and know nothing about another states existence. States are therefore a functional "black box" and decoupled from the rest of the game. The only thing a state describes is only the thing which is suggests it actually does. To keep this high level of independence, the precise chaining of states is achieved through requesting a transition to the `PlayerActionManager`. Therefore, adding states become trivial and only a matter of implementing a specific behavior and matching it to an input. The exact algorithm used in state switching is described further in section 5.2..

As one may notice on this graph, the `PlayerActionManager` and by extension all `EntityActionManager`s are not the root of the graph, and neither is the physics object responsible for the movement, despite their nature being the core or percieved core of the entire entity. The true root of the scene is the `Entity`, which acts as the interface for the entity to the game object manager, whilst also being a relatively stateless container for all components of the entity, which prevents intermingling of unrelated systems.

The view layer is considerably simpler, since it has less components. Furthermore, most components of the view layer are provided by Godot, such as the Meshes, `Animator` and `Skeleton3D`. Their outwards facing APIs are designed in such a way to only needing to be told what to do without needed to know more about the concrete state of what tells them to do so. Other parts of the view layer, which we coded ourselves follow the same philosophy. The `ValueBar`, which implements the health and for the Player specifically, the energy bar, only needs a reference to the resource it needs to display in the bar to function correctly, and the entity's resource do not have to know about the `ValueBar`s existence. Therefore, the view layer knows nothing about the model, as they are being told by the model what to do. This is best exemplified through the ability to swap out any model and skeleton for any other model-skeleton pair, given that the animations and frame data are also updated properly. The neither model or controller will not care about the change.

The controller layer is the part which differs across all entities, and no default controller implementation exists, but all controllers work the same in essence, as they all have the common goal of producing an array with the current possible intents of the character in mind. Therefore, it is also becomes possible to control the player through an AI-based controller just by swapping the `PlayerController`. This is, at the end of the day, the goal of the MVC pattern and the reason why we chose to use it in the characters, namely the decoupling of a complex and interconnected system, which enables modularity and leads to extendability.

Furthermore, due to the separation of concerns in the entity was not only executed on an implementation basis, but also in the scene itself. The afforementioned unique structure of our entities, with the static game object being the scene root instead of the component which is actually responsible for the movement (i.e. `FloatingBody` or `CharacterBody3D`), allowed us to spill the "guts" of our entities out of the physics body. Since most systems do not have the explicit need to reference the physics body, and since the physics body can actually be considered to be part of the view layer, as it is the driver for the view layer, with an API in the same "tell me what to do" style as the rest of the view layer. Hence, this separation of entity components made a lot of sense to us and helped with the organization of the scene.
